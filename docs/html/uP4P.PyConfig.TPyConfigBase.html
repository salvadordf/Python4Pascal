Unit

uP4P.PyConfig

Declaration

type TPyConfigBase = class(TInterfacedObject, IPyConfig)

Description

Class containing most parameters to configure Python. When done, the PyConfig_Clear() function must be used to release the configuration memory.

<see href="https://docs.python.org/3/c-api/init_config.html#pyconfig">See the article about PyConfig.)

Public function Read: IPyStatus;

Read all Python configuration.

Fields which are already initialized are left unchanged.

Fields for path configuration are no longer calculated or modified when calling this function, as of Python 3.11.

The TPyConfig.Read() function only parses PyConfig.argv arguments once: PyConfig.parse_argv is set to 2 after arguments are parsed. Since Python arguments are stripped from PyConfig.argv, parsing arguments twice would parse the application options as Python options.

Changed in version 3.10: The PyConfig.argv arguments are now only parsed once, PyConfig.parse_argv is set to 2 after arguments are parsed, and arguments are only parsed if PyConfig.parse_argv equals 1.

Changed in version 3.11: TPyConfig.Read() no longer calculates all paths, and so fields listed under Python Path Configuration may no longer be updated until TPy.InitializeFromConfig() is called.

Public property context_aware_warnings : boolean read Get_context_aware_warnings write Set_context_aware_warnings;

The 'context_aware_warnings' field exists to control whether the 'warnings.catch_warnings()' context manager behaves *concurrently safely*. 

- When 'context_aware_warnings' is **true**, 'catch_warnings' uses a
  'ContextVar' to store the temporarily-established warning filter
  state, so using it is safe across **threads and asyncio tasks**.
- When 'context_aware_warnings' is **false**, 'catch_warnings' falls
  back to modifying **global state** in the 'warnings' module, which
  is **not safe** in concurrent programs (thread/async behavior can
  become undefined).

It can also be set via the '-X context_aware_warnings' command-line option or the 'PYTHON_CONTEXT_AWARE_WARNINGS' environment variable. '<citation src="1"></citation>'

Public property pymalloc_hugepages : boolean read Get_pymalloc_hugepages write Set_pymalloc_hugepages;

Enable huge page support for pymalloc arenas (disabled by default). When enabled, the arena size on 64-bit platforms is increased to 2 MiB and arena allocation uses MAP_HUGETLB (Linux) or MEM_LARGE_PAGES (Windows) with automatic fallback to regular pages.

Even when compiled with this option, huge pages are not used at runtime unless the PYTHON_PYMALLOC_HUGEPAGES environment variable is set to 1. This opt-in is required because huge pages 

- carry risks on Linux: if the huge-page pool is exhausted, page faults
(including copy-on-write faults after os.fork()) deliver SIGBUS and kill
the process.
- need a special privilege on Windows. See the Windows documentation for
large pages for details. Python will fail on startup if the required
privilege SeLockMemoryPrivilege is not held by the user.

The configure script checks that the platform supports MAP_HUGETLB and emits a warning if it is not available.

On Windows, use the –pymalloc-hugepages flag with build.bat or set the UsePymallocHugepages MSBuild property.

<see href="https://docs.python.org/3.15/using/configure.html#cmdoption-with-pymalloc-hugepages">See the article about –with-pymalloc-hugepages.)

Public property sys_path_0 : string read Get_sys_path_0 write Set_sys_path_0;

PyConfig.sys_path_0 is the value that Python uses as the first entry in sys.path (sys.path[0]) when the interpreter runs.

In particular, it determines what sys.path[0] becomes for different invocation styles, for example: 

- for python -m module, sys.path[0] is set to include the current
  working directory,
- for python script.py, it's set to the script's directory,
- for python -c code / plain python, it's set to an "empty string"
  meaning the current working directory.

So, when embedding Python via the C-API, setting PyConfig.sys_path_0 lets you control that first sys.path entry explicitly (instead of letting Python compute it).

Public property thread_inherit_context : boolean read Get_thread_inherit_context write Set_thread_inherit_context;

Whether the new thread should inherit the current "execution context" from the thread that created it.

If thread_inherit_context is true, the new thread starts with that same context (so things like trace IDs, user IDs, request-scoped metadata, etc. propagate).

If it's false, the new thread runs with a fresh/default context (so context doesn't automatically carry over).
